## 六、AI 使用原则与反思

### 6.1 使用原则

1. **AI只提供思路框架和候选方案，不直接照抄**：所有输出必须经过人工讨论、修改和确认
2. **必须能解释和修改**：对于AI提出的每个概念、字段和SQL，小组成员都必须理解其含义并能调整
3. **事实和数据人工核实**：所有具体数据（字段数量、金额计算、外键关联）均由人工统计确认
4. **实际执行验证**：所有SQL脚本在本地MySQL 8.0.28环境实际执行，不依赖AI的"应该可以"
5. **记录使用过程**：详细记录每次AI使用的输入、建议、人工修改和验证结论

### 6.2 AI 的优势

1. 快速提供框架和初始结构，避免从零开始
2. 覆盖常见字段和场景，起到提醒作用
3. SQL语法参考价值高，特别是约束定义的语法格式
4. 文档框架生成效率高

### 6.3 AI 的局限性（本项目实际遇到的）

| 问题 | 具体表现 | 人工处理方式 |
|---|---|---|
| 业务逻辑错误 | INNER JOIN丢失非会员订单 | 改为LEFT JOIN |
| 版本不兼容 | information_schema.VIEWS用了不存在的CREATE_TIME列 | 改为IS_UPDATABLE和DEFINER |
| 语法错误 | SET DEFAULT ROLE用了FOR而非TO | 改为TO |
| 过度授权 | 店员可查员工表、会员可查所有会员信息 | 按最小权限原则收紧 |
| 数据不一致 | 订单金额与明细合计不符、外键引用不存在 | 逐一复算和核对 |
| 命名不规范 | 用order作表名（保留字）、驼峰命名 | 改为orders、小写+下划线 |
| 约束遗漏 | 经常缺CHECK、UNIQUE、NOT NULL | 对照设计逐一补全（共24个CHECK） |
| 脚本中断 | 反例测试实际执行导致整个脚本停止 | 改为注释形式呈现反例 |
| 密码安全 | 生成明文密码 | 改为bcrypt哈希值 |
| 场景不符 | 商品出现电子产品、支付方式全是微信 | 改为小卖部真实场景 |

### 6.4 验证结论

本项目第一阶段所有AI生成的内容均经过人工审核、修改和本地MySQL实际执行验证。AI原始内容平均保留率约32%，约68%的内容为人工修改或补充。关键设计决策（如LEFT JOIN的选择、最小权限原则、非会员订单支持、反范式设计）均由人工判断做出，AI仅提供初始参考。最终交付的所有SQL脚本均可从空数据库完整复现，所有约束和权限均通过正反例验证。
