## 四、错误提示与异常处理记录

### 4.1 错误号与提示消息映射

存储过程通过 `THROW` 抛出 50000 以上的业务错误号；应用层 `DatabaseProgramDao.translateError` 沿异常链找到 `SQLException`，将错误号 ≥50000 的业务错误转换为 `BusinessRuleException`（HTTP 409），前端只显示中文友好提示。

| 错误号 | 触发场景 | 后端提示消息 | HTTP 状态 | 前端表现 |
|--------|----------|--------------|-----------|----------|
| 50001 | 开始日期为空 | 开始日期不能为空 | 409 | 友好提示 |
| 50002 | 结束日期为空 | 结束日期不能为空 | 409 | 友好提示 |
| 50003 | 开始晚于结束 | 开始日期不能晚于结束日期 | 409 | 友好提示 |
| 50010 | 商品编号空 | 商品编号不能为空 | 409 | 友好提示 |
| 50011 | 操作员空 | 操作员工编号不能为空 | 409 | 友好提示 |
| 50012 | 调整数量为零 | 调整数量不能为零 | 409 | 友好提示 |
| 50013 | 原因为空 | 调整原因不能为空 | 409 | 友好提示 |
| 50014 | 商品不存在 | 商品不存在，无法调整库存 | 409 | 友好提示 |
| 50015 | 操作员不存在 | 操作员工不存在 | 409 | 友好提示 |
| 50016 | 无库存记录 | 该商品没有库存记录 | 409 | 友好提示 |
| 50017 | 库存不足 | 库存不足，调整后库存不能为负数 | 409 | 友好提示 |

### 4.2 函数异常的处理方式

T-SQL 函数内**禁止使用 TRY...CATCH、THROW、RAISERROR**，因此函数对非法输入统一返回 `NULL`，由调用方（Service / 存储过程）明确判断处理：

| 函数 | 异常输入 | 返回 | 调用方处理 |
|------|----------|------|------------|
| fn_restock_qty | 商品/库存不存在、空编号 | NULL | 前端不显示补货建议 |
| fn_discount_rate | 会员不存在 | NULL | 下单流程中止并提示 |
| fn_discount_amount | 负金额、折扣率超出 [0,1] | NULL | 校验失败，不写入订单 |
| fn_category_discount_rate | 分类编号不存在 | 1.000 | 不影响正常下单 |

## 五、未写入 / 不完整数据验证

为验证"校验失败时不产生脏数据"，对异常用例执行前后的库存、订单、审计记录进行对比，确认失败操作完全不写入。

### 5.1 库存不足拒绝且不写入（P13）

对 P0005 执行 −100 的非法调整（当前库存不足以扣减）：

| 验证项 | 执行前 | 执行后 | 是否变化 |
|--------|--------|--------|----------|
| 错误号 | — | 50017 | 正确抛出 |
| P0005 库存 | 15 | 15 | 不变 |
| 库存调整记录数 | 2 | 2 | 不变 |

**结论：** 事务在 CATCH 块中回滚，库存与审计表均未被修改，未写入不完整数据。

### 5.2 浏览器下单库存不足不写入

浏览器中对库存不足的商品提交订单，前端显示红色友好提示，验证数据：

| 验证项 | 结果 |
|--------|------|
| 前端提示 | 商品库存不足: 乐事薯片原味70g |
| 订单总数 | 不变 |
| 商品库存 | 不变 |
| 库存调整审计记录 | 不变 |

![业务错误提示](images/12_业务错误提示.png)

### 5.3 调整前后数量勾稽（P15）

对全部库存调整记录校验勾稽关系 `quantity_after = quantity_before + adjust_quantity`，并要求前后数量均非负，测试结果**违规条数 = 0**，所有审计记录勾稽一致。

## 七、测试结论

1. 两个存储过程、五个函数全部创建成功，接口签名与设计一致，均可被应用账户正常调用。
2. 函数测试 18/18、存储过程测试 15/15，**合计 33/33 全部通过，通过率 100%**。
3. 所有输入校验、业务规则错误均能正确抛出错误号或返回 NULL，并在前端转换为友好提示，不暴露 SQL、堆栈、路径等原始信息。
4. 库存不足、非法调整等异常用例经验证**不写入任何不完整数据**，事务回滚可靠，调整前后数量勾稽一致。
5. Spring Boot 应用已全部改为调用数据库对象，页面层只负责调用与展示，业务规则下沉到数据库，端到端流程验证通过。
