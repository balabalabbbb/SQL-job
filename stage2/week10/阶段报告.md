# 小卖部管理系统 - 第三阶段（第10周）存储过程与函数阶段报告

## 一、设计思路

### 1.1 项目背景

在前两个阶段，本项目已经完成了小卖部管理系统的数据库设计（建库建表、约束、视图、触发器）和 Spring Boot 四层 Web 应用（页面层、业务层、数据访问层、数据库层）。本周的核心任务是把原本散落在应用业务层中的关键业务规则——**补货选择、销售统计、库存调整、折扣计算**——下沉到数据库内部，封装成可重复调用的存储过程和函数，使业务规则在数据库层统一维护，并通过正常与异常数据验证其正确性，最后改造 Spring Boot 应用改为调用这些数据库对象。

### 1.2 为什么使用存储过程与函数

| 出发点 | 说明 |
|--------|------|
| 规则集中管理 | 把业务规则放进数据库，多个应用或客户端共用同一套逻辑，避免规则在不同代码中重复实现、口径不一致 |
| 减少重复调用 | 一次封装、多次调用，减少应用与数据库之间的网络往返，预编译对象执行效率更高 |
| 保证数据安全一致 | 库存调整等写操作在事务内完成并加锁，配合输入检查，防止脏数据和并发超扣 |
| 权限最小化 | 应用账户只授予对象的执行权限，不直接暴露底层表的写权限 |
| 可维护性 | 业务规则变更时只需修改数据库对象，页面层只调用、不重写规则 |

### 1.3 数据库对象总体设计

本周共创建 2 个存储过程、5 个函数，并新增 1 张审计表、2 个订单折扣字段：

```
retail_store
├── 存储过程
│   ├── usp_sales_statistics   销售统计（OUTPUT 汇总 + 明细结果集）
│   └── usp_adjust_inventory   库存调整（事务 + UPDLOCK + 审计）
├── 函数
│   ├── fn_restock_qty         补货量（标量）
│   ├── fn_sales_summary       销售汇总（内联表值）
│   ├── fn_discount_rate       折扣率（标量）
│   ├── fn_discount_amount     折扣金额（标量）
│   └── fn_category_discount_rate  分类折扣率（标量）
└── 新增表/字段
    ├── inventory_adjustment   库存调整审计表
    └── orders.discount_rate / discount_amount  订单折扣字段
```

### 1.4 关键技术决策

1. **销售统计用 OUTPUT 参数 + 一个结果集。** 整体汇总（订单数、销售数量、销售金额）通过三个 OUTPUT 参数返回，商品明细通过唯一结果集返回。这样既方便应用单独取汇总，又能避免多结果集在 `INSERT...EXEC` 接收时因列数不匹配报错。
2. **函数异常统一返回 NULL。** 由于 T-SQL 函数内禁止 TRY...CATCH、THROW、RAISERROR，对商品不存在、非法折扣等情况统一返回 NULL，由调用方明确判断处理。
3. **库存调整用显式事务 + 更新锁。** 事务内 `WITH (UPDLOCK, HOLDLOCK)` 读取当前库存，防止两个会话同时调整同一商品导致超扣；CATCH 块回滚并重新抛出错误。
4. **脚本全部可重复执行。** 存储过程、函数使用 `CREATE OR ALTER`，结构变更使用 `IF NOT EXISTS` 判断，重复执行不会报错。

## 二、实验过程

### 2.1 结构变更

执行 `00_schema_change.sql` 完成两项变更：

1. 新建库存调整审计表 `inventory_adjustment`，含外键约束（关联商品、员工）和检查约束（调整量非零、前后数量非负）。
2. 为 `orders` 表增加 `discount_rate DECIMAL(4,3)`（默认 1.000）和 `discount_amount DECIMAL(10,2)`（默认 0），并回填历史订单，保证历史订单语义为"无折扣"。

| 约束 | 作用 |
|------|------|
| fk_adj_product / fk_adj_employee | 保证调整记录的商品、操作员真实存在 |
| chk_adj_qty_nonzero | 调整数量不能为零 |
| chk_adj_before_nonneg / chk_adj_after_nonneg | 调整前后库存均不能为负 |
| chk_orders_discount_rate | 折扣率必须在 [0,1] 区间 |

### 2.2 存储过程实现

#### 2.2.1 销售统计 usp_sales_statistics

- 输入开始、结束日期，先做输入检查（日期为空、开始晚于结束），再以"次日零点"为上界实现含当天的日期范围。
- 三个 OUTPUT 参数返回整体汇总，一个结果集返回商品销售明细（仅列有销售的商品）。
- 只统计 `order_status = '已支付'` 的订单，已取消、已退款不计入销售。

#### 2.2.2 库存调整 usp_adjust_inventory

- 先做事务外基础校验（商品编号、操作员、数量、原因、商品与员工是否存在）。
- 事务内加更新锁读取库存，校验库存记录存在和调整后非负，再更新库存主表、插入审计表，最后提交。
- CATCH 块中回滚事务并重新抛出错误，保证失败时不产生脏数据。

### 2.3 函数实现

| 函数 | 类型 | 实现要点 |
|------|------|----------|
| fn_restock_qty | 标量 | 目标默认 = 阈值×2，达标返回 0，否则补到目标，不存在返回 NULL，返回值恒非负 |
| fn_sales_summary | 内联表值 | 一次查询返回商品编号/名称/数量/金额/订单数，含全部商品，可在 SELECT/JOIN 中调用 |
| fn_discount_rate | 标量 | 会员等级折扣与金额门槛取更优，冻结会员不享折扣，会员不存在返回 NULL |
| fn_discount_amount | 标量 | 折前金额 ×(1−折扣率) 四舍五入到分，非法输入返回 NULL |
| fn_category_discount_rate | 标量 | 饮料 0.98、食品 0.99，其余 1.00，未知分类不影响下单 |

### 2.5 Spring Boot 整合改造

新增 `DatabaseProgramDao`（@Repository，注入 JdbcTemplate）统一封装全部数据库对象调用：

| 调用对象 | 技术方式 |
|----------|----------|
| 标量函数 | JdbcTemplate.queryForObject |
| 表值函数 | SQL 查询 + RowMapper |
| 存储过程 | SimpleJdbcCall |
| 过程结果集 | returningResultSet 映射明细（SQL Server 风格） |

同时新增 SalesService、SalesController、sales.html，改造 InventoryService、OrderService、相关 Controller 和页面模板。下单流程改为先算折前总额，调用折扣函数，将折扣率和折扣金额写入订单，明细保持原价快照；页面层只负责调用数据库对象和展示结果，不再重写业务规则。

### 2.6 异常处理增强

整合初期，存储过程抛出的业务错误（如 50017 库存不足）被 Spring 包装成 `UncategorizedSQLException`，落到全局兜底返回 500，语义不准确。为此在 `DatabaseProgramDao` 增加 `translateError`：

- 捕获 `DataAccessException`，沿 cause 链查找 `SQLException`；
- 若错误号 ≥50000（后端预置业务校验），转换为 `BusinessRuleException`（HTTP 409），消息为中文业务提示；
- 其余异常原样抛出，后端日志完整保留原始错误号、SQL state、SQLServerException 和堆栈。

改造后，库存不足、调整数量为零、商品不存在等均返回 409 业务错误和明确中文提示，前端不暴露任何原始信息。

### 3.2 遇到的问题与解决

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| INSERT...EXEC 报错 213 | 多结果集列数与接收表变量不匹配 | 改为 OUTPUT 参数返回汇总 + 一个明细结果集 |
| 函数无法主动报错 | T-SQL 函数禁止 TRY...CATCH/THROW | 异常统一返回 NULL，由调用方处理 |
| 业务错误被包装成 500 | Spring 将 SQLException 归入 UncategorizedSQLException | 增加 translateError，错误号≥50000 转 409 业务异常 |
| 补货建议不渲染 | 页面 script 缺少 th:inline，JS 内联失效 | 改用 body 上的 data 属性传递角色标识 |
| 订单明细显示 undefined | 明细为 snake_case、脚本误用 camelCase | 按真实字段名修正，订单与明细分别处理 |
| 中文脚本执行错乱 | 无 BOM 时 sqlcmd 按 GBK 解析 | 含中文脚本统一保存为 UTF-8 with BOM |

### 3.3 心得体会

1. **业务规则下沉的价值。** 把规则放进存储过程和函数后，口径在数据库层统一，应用只负责调用，规则变更时不必在多处修改代码，复用性和一致性明显提升。
2. **存储过程与函数各有适用场景。** 需要写库、事务、主动报错的库存调整适合用存储过程；纯计算、需要在查询中反复调用的补货和折扣适合用函数。理解二者边界是本周的重要收获。
3. **事务与锁保障数据正确。** 库存调整在事务内加更新锁，并通过"未写入验证"和"前后数量勾稽"确认异常时不产生脏数据，让我对并发控制和数据一致性有了更具体的认识。
4. **错误处理要前后端配合。** 数据库抛出错误号、应用层转换语义、前端显示友好提示，原始信息只留在后端，既保证了用户体验，又保留了排查能力。
5. **可复现性靠工程化保障。** 通过可重复执行的脚本和数据重置脚本，任何测试都能从干净基线重新复现，这对结果的可信度非常重要。
