## 二、问题详细说明

### P1：订单必须至少有一条明细，数据库未强制

| 项目 | 内容 |
|---|---|
| **问题描述** | 业务规则要求每笔订单必须包含至少一条商品明细，但数据库仅通过外码保证明细引用的订单存在，无法保证订单一定有明细 |
| **业务证据** | 一笔没有任何商品的"空订单"在业务上无意义，但当前数据库允许插入 orders 记录而不插入任何 order_item |
| **影响** | 可能产生空订单，导致销售统计失真（订单数虚高）、财务核对困难 |
| **当前实现** | CRUD 脚本中使用事务（START TRANSACTION）保证创建订单时同时插入明细，但这是代码层面的保证，非数据库约束 |
| **改进方向** | 第六周可添加触发器：在 INSERT orders 后检查是否有对应明细，或在应用层强制事务；也可考虑用存储过程封装订单创建 |
| **处理方式** | 🔄 拟在第六周通过触发器或存储过程实现 |

### P2：每个商品必须有库存记录，数据库未强制

| 项目 | 内容 |
|---|---|
| **问题描述** | 业务规则要求每个商品必须有对应的库存记录（数量可为0），但数据库仅通过 inventory.product_id 的 UNIQUE 约束保证一个商品最多一条库存，无法保证每个商品都有库存 |
| **业务证据** | 新增商品时如果忘记创建库存记录，该商品将显示为"无库存信息"，影响销售和库存预警 |
| **影响** | 商品可能没有库存记录，库存查询遗漏该商品，库存预警失效 |
| **当前实现** | 样例数据中每个商品都有库存记录（人工保证），但无数据库约束 |
| **改进方向** | 第六周可添加触发器：INSERT product 后自动创建一条 inventory 记录（quantity=0）；或用存储过程封装商品创建 |
| **处理方式** | 🔄 拟在第六周通过触发器实现 |

### P3：库存变更无历史记录，仅存最后更新人

| 项目 | 内容 |
|---|---|
| **问题描述** | inventory 表仅记录 last_updated（最后更新时间）和 last_updated_by（最后更新人），不记录每次变更的历史 |
| **业务证据** | 库存变化有多种原因：销售扣减、补货入库、盘点损益、退货入库。当前设计无法追溯每次变化的原因和操作人 |
| **影响** | 无法进行库存审计、无法分析库存异常原因、无法生成库存变动报表 |
| **当前实现** | 仅记录最后更新时间和更新人，无历史表 |
| **改进方向** | 第六周可新增 inventory_log（库存变更日志）表，记录每次变更的时间、操作人、变更数量、变更原因（销售/补货/盘点/退货） |
| **处理方式** | 🔄 拟在第六周新增库存变更日志表 |

### P4：供应商无独立实体，仅存名称字符串

| 项目 | 内容 |
|---|---|
| **问题描述** | product 表的 supplier 字段仅存储供应商名称字符串，没有独立的 supplier 实体表 |
| **业务证据** | 第一周数据边界清单明确将供应商信息列为"暂不进库"，理由是第一阶段聚焦销售闭环，采购流程暂未纳入 |
| **影响** | 无法管理供应商联系方式、无法按供应商统计采购、供应商名称修改需批量更新商品表 |
| **当前实现** | product.supplier 为 VARCHAR 字段，存储供应商名称 |
| **改进方向** | 第二阶段如纳入采购流程，可新增 supplier 表，product.supplier_id 改为外码引用 |
| **处理方式** | ✅ 保留（符合第一阶段数据边界决策，后续阶段再扩展） |

### P5：UNIQUE(order_id, product_id) 限制同单同商品只能一行

| 项目 | 内容 |
|---|---|
| **问题描述** | order_item 表有 UNIQUE(order_id, product_id) 约束，假设同一订单中同一商品只出现一次 |
| **业务证据** | 小卖部场景中，同一商品在一笔订单中通常合并为一行（数量累加），不需要拆分为多行 |
| **影响** | 如果业务需要同一商品分多行（如不同折扣、不同批次），此约束会阻止 |
| **当前实现** | UNIQUE(order_id, product_id) 作为候选码 |
| **改进方向** | 如未来需要拆分行，可移除此约束，改用 item_id 作为唯一标识 |
| **处理方式** | ✅ 保留（当前小卖部场景适用，课程提示也明确说明"不要默认同一商品在一张订单中只能出现一次"，我们已分析并确认当前场景适用） |

### P6：订单状态流转无历史记录

| 项目 | 内容 |
|---|---|
| **问题描述** | orders.order_status 仅记录当前状态，不记录状态变更历史 |
| **业务证据** | 订单状态有：待支付、已支付、已退款、已取消。状态变更（如支付、退款）没有时间戳和操作人记录 |
| **影响** | 无法追溯订单状态变更时间、无法分析退款时效 |
| **当前实现** | 仅记录当前 order_status |
| **改进方向** | 后续可新增 order_status_log 表 |
| **处理方式** | ✅ 保留（第一阶段最小闭环不需要，后续阶段扩展） |

### P7：会员积分变更无历史记录

| 项目 | 内容 |
|---|---|
| **问题描述** | member.points_balance 仅记录当前积分余额，不记录积分变更历史 |
| **业务证据** | 积分获取（消费）和积分使用（兑换）没有明细记录 |
| **影响** | 无法核对积分变动、无法处理积分争议 |
| **当前实现** | 仅记录当前积分余额 |
| **改进方向** | 后续可新增 points_log 表 |
| **处理方式** | ✅ 保留（第一阶段最小闭环不需要） |

### P8：员工操作无审计日志

| 项目 | 内容 |
|---|---|
| **问题描述** | 没有统一的员工操作审计日志，关键操作（删除商品、修改价格、退款）无法追溯 |
| **业务证据** | 库存更新有 last_updated_by，但其他操作（修改商品价格、删除商品、创建订单）无操作人记录 |
| **影响** | 安全审计困难，无法追溯敏感操作 |
| **当前实现** | 仅库存表有更新人字段 |
| **改进方向** | 后续可新增 operation_log 表或在应用层记录 |
| **处理方式** | ✅ 保留（第一阶段最小闭环不需要） |

### P9：库存与商品 1:1 分表，可考虑合并

| 项目 | 内容 |
|---|---|
| **问题描述** | product 和 inventory 是 1:1 关系，理论上可以合并为一张表 |
| **业务证据** | 分表的理由：(1) 库存更新频繁，与商品基本信息分离可减少锁竞争；(2) 未来扩展多仓库时，inventory 可自然扩展为1:N；(3) 库存审计字段（更新时间、更新人）与商品属性语义不同 |
| **影响** | 多一次 JOIN 查询，但性能影响可忽略 |
| **当前实现** | 分表设计，inventory.product_id 加 UNIQUE 约束 |
| **改进方向** | 保持分表，为未来多仓库扩展留空间 |
| **处理方式** | ✅ 保留（设计合理，有明确的分管理由） |

### P10：非会员订单 member_id 为空，查询需注意 LEFT JOIN

| 项目 | 内容 |
|---|---|
| **问题描述** | 非会员订单的 member_id 为 NULL，连接查询时必须使用 LEFT JOIN 而非 INNER JOIN |
| **业务证据** | 小卖部有大量散客（非会员），这些订单的 member_id 为空 |
| **影响** | 如果误用 INNER JOIN，会丢失所有非会员订单，导致统计不准确 |
| **当前实现** | 所有涉及订单-会员连接的查询均使用 LEFT JOIN，已在第四周查询中正确处理 |
| **改进方向** | 在文档和代码注释中明确标注，避免后续开发误用 |
| **处理方式** | ✅ 保留（业务需要，已正确处理，属于使用注意事项而非设计缺陷） |

## 三、设计合理、明确保留的部分

| 设计决策 | 保留理由 |
|---|---|
| 6张表的划分 | 符合业务语义，每类对象独立管理 |
| order_id 用业务编码（ORD+日期+序号） | 有业务含义，便于人工识别和对账 |
| order_item.unit_price 冗余存储成交单价 | 记录历史成交价，防止商品涨价影响历史订单金额 |
| member.phone 加 UNIQUE 作为候选码 | 手机号天然唯一，适合作为业务标识 |
| employee.login_account 加 UNIQUE | 登录账号必须唯一 |
| 金额用 DECIMAL 而非 FLOAT | 避免浮点精度问题，财务数据必须精确 |
| 密码存 bcrypt 哈希而非明文 | 安全要求 |
| 4个角色的最小权限设计 | 符合安全原则，越权测试通过 |
| 24个CHECK约束 | 在数据库层面强制业务规则，比应用层检查更可靠 |
