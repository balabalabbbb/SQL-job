## 二、各联系详细说明

### R1：会员下单（MEMBER — ORDERS）

| 项目 | 内容 |
|---|---|
| **联系含义** | 一个会员可以下多个订单；一个订单可以属于一个会员，也可以不属于任何会员（非会员散客） |
| **MEMBER 端基数** | 0..1（一个订单对应0个或1个会员） |
| **ORDERS 端基数** | 0..N（一个会员有0个或多个订单） |
| **MEMBER 端参与约束** | 可选参与——订单可以没有会员（非会员订单） |
| **ORDERS 端参与约束** | 可选参与——会员可以从未下过订单 |
| **适用条件** | 顾客结账时如提供手机号/会员号则关联会员，否则 member_id 为 NULL |
| **对应表** | orders |
| **外码** | orders.member_id → member.member_id |
| **外码可空** | 是（允许 NULL，表示非会员订单） |
| **当前实现方式** | 数据库外码约束 + 字段允许 NULL |
| **数据库约束** | FOREIGN KEY (member_id) REFERENCES member(member_id)；无 NOT NULL 约束 |
| **业务规则检查** | 无额外检查，由外码保证引用的会员必须存在 |
| **验证结论** | ✅ 正确。LEFT JOIN 查询可同时返回会员订单和非会员订单 |

### R2：员工收银（EMPLOYEE — ORDERS）

| 项目 | 内容 |
|---|---|
| **联系含义** | 一个员工（收银员）可以处理多个订单；一个订单必须由一个收银员处理 |
| **EMPLOYEE 端基数** | 1..1（一个订单必须对应1个收银员） |
| **ORDERS 端基数** | 0..N（一个员工处理0个或多个订单） |
| **EMPLOYEE 端参与约束** | 必须参与——每笔订单必须有收银员 |
| **ORDERS 端参与约束** | 可选参与——员工可以尚未处理过订单 |
| **适用条件** | 所有订单均由店员操作收银系统生成，自动记录当前登录员工 |
| **对应表** | orders |
| **外码** | orders.cashier_id → employee.employee_id |
| **外码可空** | 否（NOT NULL） |
| **当前实现方式** | 数据库外码约束 + NOT NULL 约束 |
| **数据库约束** | FOREIGN KEY (cashier_id) REFERENCES employee(employee_id)；cashier_id NOT NULL |
| **业务规则检查** | 应用层确保创建订单时传入当前登录员工ID |
| **验证结论** | ✅ 正确。插入无 cashier_id 的订单会被 NOT NULL 约束拒绝 |

### R3：员工更新库存（EMPLOYEE — INVENTORY）

| 项目 | 内容 |
|---|---|
| **联系含义** | 一个员工可以更新多条库存记录；每条库存记录的最后更新必须由一个员工操作 |
| **EMPLOYEE 端基数** | 1..1（一条库存记录的最后更新人必须是1个员工） |
| **INVENTORY 端基数** | 0..N（一个员工更新0条或多条库存记录） |
| **EMPLOYEE 端参与约束** | 必须参与——库存记录必须有更新人 |
| **INVENTORY 端参与约束** | 可选参与——员工可以从未更新过库存 |
| **适用条件** | 库存数量变化时（销售扣减、补货入库、盘点调整）记录操作员工 |
| **对应表** | inventory |
| **外码** | inventory.last_updated_by → employee.employee_id |
| **外码可空** | 否（NOT NULL） |
| **当前实现方式** | 数据库外码约束 + NOT NULL 约束 |
| **数据库约束** | FOREIGN KEY (last_updated_by) REFERENCES employee(employee_id)；last_updated_by NOT NULL |
| **业务规则检查** | 仅记录最后更新人，**不记录更新历史**（已知局限，见问题清单） |
| **验证结论** | ✅ 正确。但仅记录最后更新人，无历史审计轨迹 |

### R4：商品拥有库存（PRODUCT — INVENTORY）

| 项目 | 内容 |
|---|---|
| **联系含义** | 一个商品必须有一条库存记录；一条库存记录必须对应一个商品 |
| **PRODUCT 端基数** | 1..1（一条库存记录必须对应1个商品） |
| **INVENTORY 端基数** | 1..1（一个商品必须有1条库存记录） |
| **PRODUCT 端参与约束** | 必须参与——库存不能脱离商品存在 |
| **INVENTORY 端参与约束** | 必须参与——商品必须有库存记录（数量可为0） |
| **适用条件** | 新增商品时必须同时创建库存记录（数量初始为0或指定值） |
| **对应表** | inventory |
| **外码** | inventory.product_id → product.product_id |
| **外码可空** | 否（NOT NULL + UNIQUE） |
| **当前实现方式** | 数据库外码约束 + UNIQUE 约束（保证1:1） |
| **数据库约束** | FOREIGN KEY (product_id) REFERENCES product(product_id)；UNIQUE(product_id)；NOT NULL |
| **业务规则检查** | ⚠️ 数据库仅保证库存记录的 product_id 唯一且引用存在，但**不保证每个商品都有库存记录**（商品可以没有库存行）。这是业务规则，当前由代码/人工保证 |
| **验证结论** | ⚠️ 部分实现。1:1关系通过UNIQUE保证一个商品最多一条库存，但"每个商品必须有库存"需应用层保证 |

### R5：订单包含明细（ORDERS — ORDER_ITEM）

| 项目 | 内容 |
|---|---|
| **联系含义** | 一个订单必须包含至少一条明细；一条明细必须属于一个订单 |
| **ORDERS 端基数** | 1..1（一条明细必须属于1个订单） |
| **ORDER_ITEM 端基数** | 1..N（一个订单必须有1条或多条明细） |
| **ORDERS 端参与约束** | 必须参与——明细不能脱离订单存在 |
| **ORDER_ITEM 端参与约束** | 必须参与——订单必须至少有一条明细（业务规则） |
| **适用条件** | 创建订单时先插入订单主表，再插入至少一条明细 |
| **对应表** | order_item |
| **外码** | order_item.order_id → orders.order_id |
| **外码可空** | 否（NOT NULL） |
| **当前实现方式** | 数据库外码约束 + NOT NULL + 事务处理（CRUD脚本中使用START TRANSACTION） |
| **数据库约束** | FOREIGN KEY (order_id) REFERENCES orders(order_id)；order_id NOT NULL |
| **业务规则检查** | ⚠️ "订单必须至少有一条明细"是业务规则，**数据库外码无法强制保证**（外码只保证明细引用的订单存在，不能保证订单有明细）。当前由CRUD脚本中的事务和代码逻辑保证 |
| **验证结论** | ⚠️ 部分实现。外码保证明细属于有效订单，但"空订单"问题需应用层/触发器保证 |

### R6：商品出现在明细中（PRODUCT — ORDER_ITEM）

| 项目 | 内容 |
|---|---|
| **联系含义** | 一个商品可以出现在多条明细中；一条明细必须对应一个商品 |
| **PRODUCT 端基数** | 1..1（一条明细必须对应1个商品） |
| **ORDER_ITEM 端基数** | 0..N（一个商品出现在0条或多条明细中） |
| **PRODUCT 端参与约束** | 必须参与——明细必须有商品 |
| **ORDER_ITEM 端参与约束** | 可选参与——商品可以从未被销售过 |
| **适用条件** | 订单明细中记录购买的商品、数量和成交单价 |
| **对应表** | order_item |
| **外码** | order_item.product_id → product.product_id |
| **外码可空** | 否（NOT NULL） |
| **当前实现方式** | 数据库外码约束 + NOT NULL |
| **数据库约束** | FOREIGN KEY (product_id) REFERENCES product(product_id)；product_id NOT NULL |
| **候选码** | UNIQUE(order_id, product_id)——假设同一订单中同一商品只出现一次 |
| **业务规则检查** | ⚠️ UNIQUE(order_id, product_id) 假设同一商品在一张订单中只出现一行。如果业务需要同一商品分多行（如不同折扣/批次），此约束会限制。当前小卖部场景下合理 |
| **验证结论** | ✅ 适用于当前场景。如未来需要拆分明细行，需移除该UNIQUE约束 |

## 三、M:N 联系分解说明

订单（ORDERS）与商品（PRODUCT）之间本质上是 **M:N** 联系：
- 一个订单包含多个商品
- 一个商品可出现在多个订单中

通过关联实体 **ORDER_ITEM（订单明细）** 分解为两个 1:N 联系：
- ORDERS 1:N ORDER_ITEM（R5）
- PRODUCT 1:N ORDER_ITEM（R6）

ORDER_ITEM 除了两个外码（order_id, product_id）外，还包含联系自身的属性：
- quantity（购买数量）
- unit_price（成交单价——记录历史成交价，有意冗余）
- subtotal（小计金额 = quantity × unit_price，有CHECK约束保证）

## 四、数据库约束 vs 业务规则对照

| 规则 | 类型 | 当前实现 | 是否充分 |
|---|---|---|---|
| 订单必须有收银员 | 数据库约束 | cashier_id NOT NULL + 外码 | ✅ 充分 |
| 订单可以没有会员 | 数据库约束 | member_id 允许 NULL | ✅ 充分 |
| 库存必须有更新人 | 数据库约束 | last_updated_by NOT NULL + 外码 | ✅ 充分 |
| 一个商品最多一条库存 | 数据库约束 | product_id UNIQUE | ✅ 充分 |
| 每个商品必须有库存 | 业务规则 | 代码/人工保证 | ⚠️ 不充分，建议触发器 |
| 订单必须至少一条明细 | 业务规则 | 事务+代码保证 | ⚠️ 不充分，建议触发器 |
| 明细小计=数量×单价 | 数据库约束 | CHECK(subtotal = quantity*unit_price) | ✅ 充分 |
| 进价≤售价 | 数据库约束 | CHECK(purchase_price <= sale_price) | ✅ 充分 |
| 手机号11位 | 数据库约束 | CHECK(phone REGEXP '^[0-9]{11}$') | ✅ 充分 |
| 同一订单同一商品只一行 | 数据库约束 | UNIQUE(order_id, product_id) | ✅ 当前场景适用 |
| 库存更新有历史记录 | 业务规则 | 仅记录最后更新人 | ❌ 未实现，需新增库存变更日志表 |
