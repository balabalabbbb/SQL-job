# 第五周阶段报告 — ER 模型设计与验证

## 一、设计思路

### 1.1 从 v0.1 关系模式反推 ER 模型

第一阶段（第1-4周）完成了 v0.1 数据库原型，包含6张表、49个字段。第五周从已有的关系模式反推 ER 模型，目的是：
1. 验证表设计是否合理，实体和联系是否清晰
2. 发现实体遗漏、属性重复或联系表达不清的问题
3. 为第六周的规范化和迁移调整提供依据

### 1.2 实体识别

从6张表中识别出6个实体：

| 实体 | 对应表 | 主码 | 候选码 | 业务含义 |
|---|---|---|---|---|
| 会员 MEMBER | member | member_id | phone | 注册会员顾客 |
| 员工 EMPLOYEE | employee | employee_id | login_account | 店铺工作人员 |
| 商品 PRODUCT | product | product_id | 无 | 小卖部售卖的商品 |
| 库存 INVENTORY | inventory | inventory_id | product_id | 商品的库存状态 |
| 订单 ORDERS | orders | order_id | 无 | 顾客的交易订单 |
| 订单明细 ORDER_ITEM | order_item | item_id | (order_id, product_id) | 订单中商品的购买记录 |

**实体判断理由**：
- 会员、员工、商品、订单是典型的独立实体，有明确的业务含义和唯一标识
- 库存虽然与商品是1:1关系，但独立成表有利于审计（更新时间、更新人）和未来多仓库扩展
- 订单明细是订单与商品之间M:N联系的关联实体，包含数量、单价等联系自身的属性

### 1.3 联系识别

共识别出6个联系：

| 联系 | 实体间关系 | 基数 | 实现方式 |
|---|---|---|---|
| 下单 | MEMBER — ORDERS | 1:N（两端可选） | orders.member_id 外码，可空 |
| 收银 | EMPLOYEE — ORDERS | 1:N（员工端必须） | orders.cashier_id 外码，NOT NULL |
| 更新库存 | EMPLOYEE — INVENTORY | 1:N（员工端必须） | inventory.last_updated_by 外码，NOT NULL |
| 拥有库存 | PRODUCT — INVENTORY | 1:1（两端必须） | inventory.product_id 外码 + UNIQUE |
| 包含明细 | ORDERS — ORDER_ITEM | 1:N（订单端必须-业务规则） | order_item.order_id 外码，NOT NULL |
| 商品出现在明细 | PRODUCT — ORDER_ITEM | 1:N（商品端可选） | order_item.product_id 外码，NOT NULL |

### 1.4 基数与参与约束分析

**关键设计决策**：
1. **会员与订单是两端可选的1:N**：会员可以没有订单（新注册会员），订单可以没有会员（非会员散客）。这是小卖部场景的重要特征，member_id 允许 NULL。
2. **员工与订单是员工端必须的1:N**：每笔订单必须有收银员，但员工可以尚未处理过订单。
3. **商品与库存是1:1**：一个商品对应一条库存记录，通过 UNIQUE(product_id) 保证。
4. **订单与明细是订单端必须的1:N（业务规则）**：每笔订单必须至少有一条明细，但数据库外码无法强制，需触发器或应用层保证。

## 二、典型场景在 ER 图与数据库中的对应关系

### 2.1 场景一：多商品订单

**业务描述**：顾客购买了3种商品（牛奶、方便面、笔），生成一笔订单，包含3条明细。

**ER 图中的表示**：
```
ORDERS (1) —— 包含 —— (N) ORDER_ITEM (N) —— 出现在 —— (1) PRODUCT
  │                                          │
  └─ order_id = ORD202609160001              ├─ product_id = P0001 (牛奶)
  └─ total_amount = 10.00                    ├─ product_id = P0002 (方便面)
  └─ cashier_id = 2                          └─ product_id = P0003 (笔)
```

**数据库中的对应**：

```sql
-- 订单主表（1行）
INSERT INTO orders (order_id, order_time, total_amount, payment_method, order_status, cashier_id)
VALUES ('ORD202609160001', '2026-09-16 10:00:00', 10.00, '现金', '已完成', 2);

-- 订单明细（3行，对应3个商品）
INSERT INTO order_item (order_id, product_id, quantity, unit_price, subtotal) VALUES
('ORD202609160001', 'P0001', 2, 3.50, 7.00),
('ORD202609160001', 'P0002', 1, 4.50, 4.50),
('ORD202609160001', 'P0003', 1, 2.00, 2.00);
-- 注意：实际total_amount应为13.50，此处仅为示例
```

**对应关系验证**：
- ER图中 ORDERS 1:N ORDER_ITEM → 数据库中一笔订单对应多行明细 ✅
- ER图中 PRODUCT 1:N ORDER_ITEM → 数据库中一个商品可出现在多行明细 ✅
- M:N联系通过关联实体ORDER_ITEM分解为两个1:N联系 ✅
- ORDER_ITEM包含联系自身属性（quantity, unit_price, subtotal）✅

### 2.2 场景二：会员购买 vs 散客购买

**业务描述**：
- 会员"张三"（member_id=1）购买商品，订单关联会员
- 散客（非会员）购买商品，订单不关联会员

**ER 图中的表示**：
```
MEMBER (0..1) —— 下单 —— (0..N) ORDERS
    │                              │
    ├─ member_id=1 (张三)          ├─ order_id=ORD001 (会员订单, member_id=1)
    └─ (无对应会员)                 └─ order_id=ORD002 (散客订单, member_id=NULL)
```

**数据库中的对应**：

```sql
-- 会员订单：member_id 有值
INSERT INTO orders (order_id, member_id, cashier_id, total_amount, ...)
VALUES ('ORD001', 1, 2, 15.00, ...);

-- 散客订单：member_id 为 NULL
INSERT INTO orders (order_id, member_id, cashier_id, total_amount, ...)
VALUES ('ORD002', NULL, 2, 8.50, ...);
```

**查询验证**：

```sql
-- 必须用 LEFT JOIN，否则散客订单会丢失
SELECT o.order_id, m.member_name, o.total_amount
FROM orders o
LEFT JOIN member m ON o.member_id = m.member_id;
-- 结果：ORD001 张三 15.00 / ORD002 NULL 8.50
```

**对应关系验证**：
- ER图中 MEMBER 端基数 0..1 → 数据库中 member_id 允许 NULL ✅
- ER图中 ORDERS 端基数 0..N → 会员可以没有订单 ✅
- 查询必须用 LEFT JOIN 而非 INNER JOIN ✅

### 2.3 场景三：库存查询

**业务描述**：查询所有库存低于阈值的商品，触发补货预警。

**ER 图中的表示**：
```
PRODUCT (1) —— 拥有 —— (1) INVENTORY
    │                        │
    ├─ product_id=P0005      ├─ quantity=8, min_threshold=10 (需补货)
    └─ product_name=薯片     └─ last_updated_by=2
```

**数据库中的对应**：

```sql
-- 1:1 连接查询库存预警商品
SELECT p.product_id, p.product_name, i.quantity, i.min_threshold,
       CASE WHEN i.quantity = 0 THEN '缺货'
            WHEN i.quantity < i.min_threshold THEN '需补货'
            ELSE '正常' END AS 库存状态
FROM product p
JOIN inventory i ON p.product_id = i.product_id
WHERE i.quantity < i.min_threshold;
-- 结果：P0005 薯片 8 10 需补货
```

**对应关系验证**：
- ER图中 PRODUCT 1:1 INVENTORY → 数据库中通过 UNIQUE(product_id) 保证 ✅
- 库存更新记录操作人（last_updated_by → employee）✅
- 1:1关系用 INNER JOIN 即可（两边都必须参与）✅

## 三、ER 图与表设计对照

| ER 图元素 | 数据库实现 | 对应表/约束 |
|---|---|---|
| 实体 MEMBER | 表 member | 9字段，主码member_id，候选码phone |
| 实体 EMPLOYEE | 表 employee | 9字段，主码employee_id，候选码login_account |
| 实体 PRODUCT | 表 product | 10字段，主码product_id |
| 实体 INVENTORY | 表 inventory | 7字段，主码inventory_id，候选码product_id |
| 实体 ORDERS | 表 orders | 8字段，主码order_id |
| 实体 ORDER_ITEM | 表 order_item | 6字段，主码item_id，候选码(order_id,product_id) |
| 联系 下单(MEMBER-ORDERS) | 外码 orders.member_id | 可空，FOREIGN KEY |
| 联系 收银(EMPLOYEE-ORDERS) | 外码 orders.cashier_id | NOT NULL，FOREIGN KEY |
| 联系 更新库存(EMPLOYEE-INVENTORY) | 外码 inventory.last_updated_by | NOT NULL，FOREIGN KEY |
| 联系 拥有(PRODUCT-INVENTORY) | 外码 inventory.product_id | NOT NULL + UNIQUE |
| 联系 包含(ORDERS-ORDER_ITEM) | 外码 order_item.order_id | NOT NULL，FOREIGN KEY |
| 联系 出现在(PRODUCT-ORDER_ITEM) | 外码 order_item.product_id | NOT NULL，FOREIGN KEY |
| M:N 联系(ORDERS-PRODUCT) | 关联实体 ORDER_ITEM | 含quantity, unit_price, subtotal |

## 四、发现的问题与改进方向

通过 ER 模型反推，发现 v0.1 设计存在以下问题（详见 `v0.1问题清单.md`）：

### 高优先级（第六周拟调整）
1. **订单必须至少有一条明细**：业务规则，数据库未强制 → 拟加触发器
2. **每个商品必须有库存记录**：业务规则，数据库未强制 → 拟加触发器
3. **库存变更无历史记录**：仅存最后更新人 → 拟新增 inventory_log 表

### 中低优先级（保留，后续阶段扩展）
4. 供应商无独立实体 → 符合第一阶段数据边界，保留
5. UNIQUE(order_id, product_id) → 当前场景适用，保留
6. 订单状态/积分/操作无历史记录 → 第一阶段最小闭环，保留

### 设计合理、明确保留的部分
- 6张表的划分符合业务语义
- order_id 用业务编码便于对账
- order_item.unit_price 冗余存储历史成交价
- 金额用 DECIMAL、密码存 bcrypt 哈希
- 4个角色最小权限设计
- 24个CHECK约束在数据库层面强制业务规则

| 典型场景验证 | ✅ | 多商品订单、会员/散客购买、库存查询 |

### 关键发现

1. **ER模型是验证表设计的有效工具**：从关系模式反推ER图，能发现"业务规则未在数据库强制"的问题（如空订单、商品无库存）。
2. **1:1关系需要明确分管理由**：商品与库存1:1分表，理由是审计字段分离和未来多仓库扩展，否则可以合并。
3. **M:N联系必须通过关联实体实现**：订单与商品的M:N通过订单明细实现，关联实体包含联系自身的属性（数量、单价）。
4. **可选参与需要外码允许NULL**：会员与订单的联系两端可选，member_id允许NULL，查询必须用LEFT JOIN。
5. **数据库约束≠业务规则**：外码只能保证引用存在，不能保证"至少一条明细"这类业务规则，需要触发器或应用层补充。
