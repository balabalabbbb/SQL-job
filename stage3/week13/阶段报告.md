# 小卖部管理系统 - 第三阶段（第10—13周）阶段报告 v2.0

## 一、设计思路

### 1.1 阶段目标

在第一阶段数据库原型和第二阶段规范化与 Spring Boot 应用的基础上，本阶段把关键业务规则下沉到数据库内部，完成可复用的存储过程、函数、触发器，使用窗口函数与递归查询完成较复杂的数据分析，并通过订单完成与补货入库两个业务事务，理解事务的原子性、锁、隔离级别和死锁，最终形成可从测试基线重复运行的版本 v2.0。

### 1.2 总体设计

| 维度 | 主要对象 | 解决的问题 |
|------|----------|------------|
| 数据库程序对象 | 2 个存储过程、5 个函数、2 个触发器 | 业务规则集中管理、统一口径、权限最小化 |
| 高级查询 | 窗口函数、递归 CTE | 在保留明细的同时统计；查询层级分类后代 |
| 业务事务 | 订单完成、补货入库存储过程 | 多表修改的原子提交与失败回滚 |
| 并发控制 | 双会话锁/隔离/死锁实验 | 观察阻塞、隔离现象与死锁，并通过统一访问顺序改进 |

### 1.3 数据库程序对象的职责划分

**存储过程（适合写库、事务、主动报错）**

| 对象 | 输入 | 输出/行为 | 异常处理 |
|------|------|-----------|----------|
| `usp_sales_statistics` | 起止日期 | 3 个 OUTPUT 汇总 + 1 个明细结果集，仅统计已支付订单 | 日期非法以 50001~50003 抛错 |
| `usp_adjust_inventory` | 商品、操作员、数量、原因 | 事务 + UPDLOCK 调整库存并写审计 | CATCH 回滚并重新抛出 |

**函数（适合纯计算、查询内复用）**

| 对象 | 类型 | 职责 |
|------|------|------|
| `fn_restock_qty` | 标量 | 计算建议补货量，达标返回 0，不存在返回 NULL |
| `fn_sales_summary` | 内联表值 | 一次返回全部商品的数量/金额/订单数，可在 SELECT/JOIN 调用 |
| `fn_discount_rate` / `fn_discount_amount` / `fn_category_discount_rate` | 标量 | 会员与分类折扣率、折扣金额计算 |

T-SQL 函数内禁止 TRY...CATCH/THROW，函数对非法输入统一返回 NULL，由调用方判断；存储过程则通过 THROW 抛出 50000 以上业务错误号。

**触发器（自动执行、处理多行）**

| 对象 | 触发时机 | 职责 |
|------|----------|------|
| `trg_inventory_audit` | inventory 的 INSERT/UPDATE/DELETE | 自动写 `inventory_change_log`，用集合处理 inserted/deleted，数量未变化不记 |
| `trg_order_complete_check` | orders 更新为已完成 | 校验明细、商品、数量、金额一致性与库存充足，不满足则回滚报错 |

### 1.4 调用关系

- 应用层（`DatabaseProgramDao`）只负责调用数据库对象并展示结果，不再重写业务规则；
- 订单完成事务先更新订单状态（触发器做规则校验、不扣库存），再由存储过程统一带条件扣减库存，保证一次业务只扣一次；
- 库存审计触发器在同一事务内写日志，事务回滚时库存、调整流水、审计日志一并回滚。

## 二、实验过程

### 2.1 高级查询

**窗口函数（第11周）**：窗口函数不减少原始行数，而是在每行旁增加统计结果。
- 排名：用 `RANK / DENSE_RANK / ROW_NUMBER` 按销售数量、金额或订单数对商品排名，并列处理方式各有差异；
- 累计值：以订单日期或商品顺序为明确排序字段，用 `SUM(...) OVER(ORDER BY ..)` 计算累计销售金额/数量；
- 移动平均：用 `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` 等限定窗口，计算最近 3 笔/3 天/3 个月平均，窗口大小与业务用途明确。

**递归查询（第12周）**：在 `category_hierarchy`（带 parent_id 自引用）上用递归 CTE，从指定分类出发，由起点、递归连接和终止条件查出全部后代，输出编号、父级、层级和路径；分别对根、中间、叶子和不存在编号验证，路径列在起始与递归部分保持一致类型与长度，并设置 `MAXRECURSION` 上限。

### 2.2 业务事务

**订单完成事务 `usp_complete_order_transaction`**：前置拒绝不存在/已完成/无明细订单；事务内先改状态触发校验，再用带条件的集合 UPDATE 扣库存（`WHERE quantity >= 汇总需求量`），并核对受影响行数等于涉及商品数，否则定位问题商品报 52005 回滚；全部成功才提交。

**补货入库事务 `usp_restock_inbound_transaction`**：仅待入库单据可执行；事务内带 UPDLOCK 读库存、增加库存、写调整流水，再更新单据状态与入库时间；`@simulate_fail=1` 可在部分写入后主动抛错，验证回滚。重复执行已入库单据被拒绝，不会重复加库存。

### 2.3 并发控制（第13周）

用两个独立 sqlcmd 会话（A、B）连接同一测试库，以 `@@SPID` 确认会话不同，把每个实验拆为 A1/B1/A2 步骤并标注暂停、提交、回滚与重置，第三个连接采集 `sys.dm_exec_requests`、`sys.dm_tran_locks`。

1. **写入等待**：A 扣 P 2 件不提交，B 给 P 加 5 件被阻塞（LCK_M_U 等待键锁）；A 提交 P=13、A 回滚 P=15。
2. **脏读对照**：READ UNCOMMITTED 读到未提交的 15（脏读），A 回滚后真实为 10；READ COMMITTED 以 LCK_M_S 等待，只读到已提交的 10。
3. **隔离级别对照**：READ COMMITTED 下两次读取间被补货，出现 10→15 不可重复读；REPEATABLE READ 保留共享锁，B 等待，A 两次都读 10。
4. **死锁与改进**：A 持 P 等 Q、B 持 Q 等 P 形成循环，死锁监视器终止 B 并报 1205；统一按 product_id 升序更新后只剩单向普通等待，无死锁。
5. **业务回归**：P=10 时两个会话竞争购买 P×6，仅一单成功、另一单报 52005 回滚，最终 P=4，失败订单保持待支付。

## 三、实验总结

### 3.1 完成情况

| 要求 | 状态 | 说明 |
|------|------|------|
| 存储过程与函数 | 完成 | 规则下沉、可重复调用、异常口径明确 |
| 触发器与窗口函数 | 完成 | 触发器多行处理；排名/累计/移动平均均有业务含义 |
| 递归查询与业务事务 | 完成 | 层级结果正确；提交/回滚/重复调用验证通过 |
| 并发控制 | 完成 | 阻塞、隔离、死锁证据齐全，按序更新改进有效 |
| 可重复运行 | 完成 | 从 00_init 基线即可重放，结束 @@TRANCOUNT=0 |

### 3.2 关键认识

1. **业务规则下沉提升一致性**：规则在数据库层统一，应用只调用，变更时不必多处修改。
2. **事务与锁保障数据正确**：带条件更新和行数检查避免超卖；回滚能完整撤销同一事务内的全部修改，包括审计日志。
3. **隔离级别各有边界**：READ COMMITTED 防脏读但不防不可重复读；REPEATABLE READ 保护已读数据但不防幻行，不能认为解决所有并发问题。
4. **死锁可通过访问顺序治理**：统一资源访问顺序能消除循环等待；普通等待是正常的串行化，不应与死锁混淆。
5. **错误处理与重试要谨慎**：1205 后应重试整个业务事务并限次，不能只补跑最后一句造成重复扣减。

### 3.3 后续改进方向

- 引入 SERIALIZABLE 与快照隔离的进一步对比，结合扩展事件持续监控死锁；
- 为数据库对象补充自动化回归与并发压力测试；
- 完善数据库对象版本管理与变更说明。
