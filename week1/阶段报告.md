# 第一周 - 阶段报告

## 一、设计思路

### 1.1 场景选择

本项目选择**校园小卖部**作为数据库设计的真实经营场景，选择理由如下：

- **熟悉度高**：小组成员均为在校学生，对小卖部的日常运营流程非常熟悉，能够准确梳理业务流程和识别数据对象
- **复杂度适中**：小卖部场景既不会过于简单（只有商品和订单），也不会过于复杂（涉及多仓库、多门店、供应链管理），适合作为课程项目的练手场景
- **核心对象完整**：小卖部场景天然包含商品、库存、订单、订单明细、会员、员工六类核心对象，能够覆盖关系数据库设计的主要知识点
- **可扩展性强**：在基础闭环之上，可以逐步扩展促销管理、采购管理、盘点管理、报表分析等功能，满足17周课程的进阶需求

### 1.2 设计目标

第一周的核心目标是**完成需求分析和业务建模**，为后续的关系模式设计和数据库实现奠定基础。具体目标包括：

1. 明确小卖部的业务边界，梳理从顾客进店到完成交易的完整业务流程
2. 识别所有经营角色，明确各角色的职责和权限边界，为后续权限设计提供依据
3. 划定数据边界，明确哪些信息需要进入数据库存储，哪些不需要，以及各自的理由
4. 确保六类核心对象（商品、库存、订单、订单明细、会员、员工）全部覆盖

### 1.3 设计方法

本周采用**面向对象的需求分析方法**，按照以下步骤推进：

1. **场景调研**：回忆和讨论校园小卖部的实际运营情况，列出所有可能的业务场景
2. **角色识别**：从业务场景中提取参与角色，分析各角色的行为和职责
3. **流程梳理**：按角色视角梳理业务流程，确保每个环节都有明确的执行者和数据交互
4. **数据抽象**：从业务流程中提取需要持久化的数据对象，分析数据对象之间的关联关系
5. **边界划定**：根据最小闭环原则，判断每项数据是否需要进库，排除非核心和隐私敏感数据

## 二、实验过程

### 2.1 组队与仓库创建

- **时间**：第1周第1天
- **参与人员**：全体成员
- **工作内容**：
  - 确定小组成员分工（成员A负责业务流程，成员B负责角色职能，成员C负责数据边界和工程维护）
  - 在GitHub创建远程仓库 `SQL-job`
  - 搭建项目目录结构（week1至week4）
  - 初始化README.md，明确项目范围和整体链路

### 2.2 场景确定与讨论

- **时间**：第1周第1-2天
- **参与人员**：全体成员
- **工作内容**：
  - 讨论候选场景：小卖部 vs 奶茶店 vs 其他
  - 最终确定场景：校园小卖部
  - 明确场景边界：单门店、线下到店消费、不涉及线上外卖和配送
  - 确认核心对象：商品、库存、订单、订单明细、会员、员工六类必须覆盖

### 2.3 业务流程梳理

- **时间**：第1周第3-4天
- **负责人**：成员A（主笔），全体成员讨论确认
- **工作内容**：
  - 梳理核心业务流程：顾客进店→浏览商品→挑选商品→店员结账→支付→扣减库存→会员积分
  - 扩展流程：会员注册流程、库存监控与补货流程、库存盘点流程、员工交接班流程、退货退款流程
  - 绘制业务流程图（文字描述版），确保覆盖从顾客到完成交易的主要环节
  - 交叉评审：成员B核对流程中涉及的角色是否齐全，成员C核对每个环节是否有对应数据存储

### 2.4 角色与职能分析

- **时间**：第1周第3-4天
- **负责人**：成员B（主笔），全体成员讨论确认
- **工作内容**：
  - 识别四类核心角色：店长、店员、会员、非会员顾客
  - 详细分析每个角色的核心职责、可操作数据范围、不可操作/受限项
  - 制作角色权限对比矩阵，直观展示各角色对不同数据的操作权限
  - 提出后续权限设计要点：RBAC模型、行级权限、敏感字段加密、操作审计日志
  - 交叉评审：成员A核对角色是否覆盖业务流程中的所有操作人，成员C核对角色对应的数据是否都纳入了进库范围

### 2.5 数据边界划定

- **时间**：第1周第4-5天
- **负责人**：成员C（主笔），全体成员讨论确认
- **工作内容**：
  - 制定数据边界划分原则：交易核心原则、持久化原则、可查询原则、关联原则、最小化原则、隐私保护原则
  - 逐项分析六类核心对象的字段，确定进库数据清单（共51个字段）
  - 明确不进库数据清单（共14项），并说明不进库理由和后续是否可能扩展
  - 验证六类核心对象全部覆盖，数据边界符合最小闭环原则
  - 交叉评审：成员A核对流程中的每个环节是否都有对应的数据存储，成员B核对各角色可操作的数据是否都在进库范围内

### 2.6 文档汇总与提交

- **时间**：第1周第6-7天
- **参与人员**：全体成员
- **工作内容**：
  - 汇总README.md：项目范围、环境要求、整体链路、目录结构、复现步骤
  - 撰写阶段报告：设计思路、实验过程、实验总结
  - 整理AI使用记录：记录AI协助的内容和人工修改情况
  - 填写组内分工表：明确各成员的分工和贡献
  - 全体成员最终评审，确认无误后提交到GitHub仓库

### 3.3 遇到的问题与解决

| 问题 | 解决方式 |
|---|---|
| 业务流程中是否包含退货退款存在争议 | 讨论后决定作为扩展流程包含，因为退货是零售场景的常见操作，但第一周不深入实现 |
| 员工薪资和身份证号是否进库 | 考虑到隐私敏感性和第一周最小闭环原则，决定第一周不进库，后续人事模块可加密存储 |
| 商品图片是否进库 | 第一周纯文字描述即可，决定不进库，后续可加图片URL字段扩展 |
| 非会员顾客是否需要存储个人信息 | 决定完全不存储，非会员订单不关联任何个人身份信息，保护隐私 |

### 3.4 后续工作展望

第二周将进入**关系模式设计**阶段，主要工作包括：

1. 将本周识别的六类核心对象转化为关系模式（表结构）
2. 定义每个表的属性、域、主码、候选码和外码
3. 设计表与表之间的关联关系（一对多、多对多）
4. 准备样例元组（真实数据），用于后续测试
5. 确保关系模式满足第三范式（3NF），减少数据冗余

第三周将进入**DDL与数据修改**阶段，主要工作包括：

1. 用SQL脚本创建数据库和所有表
2. 完成商品、库存、订单等对象的增删改查（CRUD）
3. 确保建库和CRUD语句能够复现

第四周将进入**连接查询、视图、完整性与授权**阶段，主要工作包括：

1. 完成多表连接查询
2. 创建统计视图
3. 实现主外键约束和检查约束
4. 设计角色权限，实现授权管理

### 3.5 心得体会

通过第一周的需求分析工作，小组成员深刻体会到：

- **需求分析是数据库设计的基础**：清晰的业务流程和明确的数据边界，能够大大减少后续设计和实现阶段的返工
- **角色权限设计要提前考虑**：在需求阶段就明确各角色的权限边界，后续数据库的授权设计才能有的放矢
- **最小化原则很重要**：第一周只保留最小闭环所需的数据，避免过度设计导致复杂度失控，后续再逐步扩展
- **团队协作效率高**：三人分工明确，各负责一个模块，交叉评审确保质量，比一个人独立完成效率更高
