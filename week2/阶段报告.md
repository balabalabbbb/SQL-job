# 第二周 - 阶段报告

## 一、设计思路

### 1.1 本周目标

第二周的核心目标是**将第一周确定的业务对象正式转化为关系模式**，具体包括：
- 确定进库的实体，为每个实体设计一张表
- 定义每张表的字段（属性+域），包括字段名、类型、长度/精度、是否允许空、默认值、取值范围、含义
- 为每张表标注主码（PK）、候选码（UNIQUE）、外码（FK）
- 为每张表编写2-3行真实业务数据作为样例元组

### 1.2 设计原则

本周关系模式设计遵循以下原则：

1. **命名统一规范**：表名和字段名全部小写，使用下划线分隔，避免SQL保留字（订单表用orders而非order）
2. **数据类型合理**：金额用DECIMAL避免浮点误差，时间用DATE/DATETIME，枚举用VARCHAR配合CHECK约束
3. **主码选择恰当**：业务编码表（商品、会员、订单）使用有意义的业务编码作为主码；操作记录表（库存、订单明细、员工）使用自增整数作为主码
4. **外码关联清晰**：所有表间关系通过外码明确，外码字段与引用表主码同名，便于理解
5. **满足第三范式**：消除部分依赖和传递依赖，减少数据冗余；仅对成交单价等需要记录历史的字段做有意冗余
6. **字段完整够用**：基于第一周数据边界清单，确保每个进库字段都有对应表字段，同时不过度设计

### 1.3 表间关系设计

六张表之间的关系如下：
- **商品-库存**：1:1关系，一个商品对应一条库存记录
- **商品-订单明细**：1:N关系，一个商品可以出现在多个订单明细中
- **订单-订单明细**：1:N关系，一个订单包含多个明细
- **会员-订单**：1:N关系，一个会员可以有多个订单（非会员订单member_id为空）
- **员工-订单**：1:N关系，一个收银员可以处理多个订单
- **员工-库存**：1:N关系，一个员工可以更新多条库存记录

## 二、实验过程

### 2.1 实体确定与表名设计

- **时间**：第2周第1天
- **参与人员**：全体成员
- **工作内容**：
  - 回顾第一周数据边界清单，确认六类核心对象：商品、库存、订单、订单明细、会员、员工
  - 为每个实体确定表名：product、inventory、orders、order_item、member、employee
  - 讨论表名命名规范，确定全部小写、下划线分隔、避免保留字的规则
  - 确认订单表使用orders而非order（order是SQL保留字）

### 2.2 字段定义与域设计

- **时间**：第2周第2-3天
- **负责人**：成员A（商品、库存）、成员B（订单、订单明细）、成员C（会员、员工）
- **工作内容**：
  - 为每张表的每个字段定义：字段名、类型、长度/精度、是否允许空、默认值、域（取值范围/枚举）、字段含义
  - 商品表10个字段：编号、名称、分类、销售价、进货价、单位、供应商、生产日期、保质期、状态
  - 库存表7个字段：记录编号、商品编号、数量、货架位置、最低阈值、最后更新时间、最后更新人
  - 订单表8个字段：订单编号、下单时间、总金额、支付方式、订单状态、会员编号、收银员编号、备注
  - 订单明细表6个字段：明细编号、订单编号、商品编号、数量、成交单价、小计
  - 会员表9个字段：会员编号、姓名、手机号、注册时间、积分余额、等级、累计消费、最后消费时间、状态
  - 员工表9个字段：员工编号、姓名、岗位、登录账号、登录密码、手机号、入职时间、状态、最后登录时间
  - 统一数据类型选择：金额用DECIMAL，时间用DATE/DATETIME，枚举用VARCHAR

### 2.3 码标注与关系验证

- **时间**：第2周第4天
- **参与人员**：全体成员
- **工作内容**：
  - 为每张表确定主码：product_id、inventory_id、order_id、item_id、member_id、employee_id
  - 识别候选码并设置UNIQUE约束：inventory.product_id、member.phone、employee.login_account
  - 标注所有外码及引用关系：共6个外码
  - 绘制表间关系图，验证所有关系都有对应的外码支撑
  - 检查是否存在遗漏的关联：确认订单-会员、订单-收银员、订单明细-商品、库存-商品、库存-更新人都已覆盖

### 2.4 样例元组编写

- **时间**：第2周第5天
- **负责人**：各表负责人编写自己负责的表
- **工作内容**：
  - 为每张表编写2-3行真实业务数据
  - 确保样例数据之间的关联一致性：订单明细中的order_id和product_id必须在订单表和商品表中存在
  - 确保样例数据符合域约束：如支付方式只能是现金/微信/支付宝，商品状态只能是在售/下架/缺货
  - 交叉验证：成员A检查成员B的订单明细与订单表的金额是否一致，成员B检查成员C的会员积分与订单消费是否匹配

### 2.5 文档汇总与评审

- **时间**：第2周第6-7天
- **参与人员**：全体成员
- **工作内容**：
  - 汇总所有表设计到《表清单与关系模式设计.md》
  - 增加设计说明部分：命名规范、数据类型选择、完整性约束、范式说明、与第一周数据边界的对应
  - 全体成员交叉评审，检查字段完整性、码标注正确性、样例数据一致性
  - 撰写阶段报告、AI使用记录、组内分工表
  - 确认无误后提交到GitHub仓库

### 3.3 遇到的问题与解决

| 问题 | 解决方式 |
|---|---|
| 订单表名用order还是orders | order是SQL保留字，最终确定用orders，避免SQL语句中需要加引号 |
| 订单明细中是否需要存unit_price | 讨论后决定需要存储，因为商品价格可能变动，历史订单应记录成交时的价格，这是有意的反范式设计 |
| 库存表的主码用product_id还是单独的inventory_id | 决定用自增的inventory_id作为主码，product_id作为外码并加UNIQUE约束，语义更清晰 |
| 非会员订单的member_id怎么处理 | 决定member_id允许为空，非会员订单该字段为NULL，外码约束在NULL时不强制校验 |
| 员工密码字段存明文还是哈希 | 决定存储bcrypt哈希值，字段长度设为64，严禁明文存储，样例数据中用哈希值占位 |
| 样例数据中订单金额与明细合计不一致 | 交叉评审时发现，已修正，确保订单total_amount等于该订单所有明细subtotal之和 |

### 3.4 后续工作展望

第三周将进入**DDL与数据修改**阶段，主要工作包括：

1. 根据本周的关系模式设计，编写SQL建库脚本（CREATE DATABASE、CREATE TABLE）
2. 定义所有约束：主码约束、外码约束、UNIQUE约束、CHECK约束、NOT NULL约束、DEFAULT默认值
3. 编写样例数据的INSERT语句，将本周的样例元组导入数据库
4. 完成商品、库存、订单等对象的增删改查（CRUD）SQL语句
5. 确保从空库开始可以一键复现整个数据库构建过程
6. 现场演示一组CRUD操作，验证数据修改的正确性

第四周将进入**连接查询、视图、完整性与授权**阶段，主要工作包括：

1. 编写多表连接查询语句（如查询某会员的所有订单明细、查询某商品的销售统计）
2. 创建统计视图（如每日销售统计视图、商品销量排行视图、会员消费排行视图）
3. 完善主外键/检查约束，验证非法数据被拒绝
4. 设计角色权限，实现店长、店员、会员的不同授权，验证越权操作失败

### 3.5 心得体会

通过第二周的关系模式设计，小组成员深刻体会到：

- **需求分析是设计的基础**：第一周清晰的数据边界清单大大加快了本周的表设计速度，每个字段都有明确的业务来源
- **命名规范很重要**：统一的命名规范让表结构清晰易读，多人协作时避免歧义，也减少了后续SQL编写的出错率
- **主码和外码是关系的灵魂**：通过主码和外码的设计，表与表之间的关系变得清晰可追溯，这是关系数据库的核心优势
- **范式与冗余需要权衡**：严格遵守第三范式可以减少冗余，但某些场景（如记录历史成交价格）需要有意冗余，要根据业务需求权衡
- **样例数据是最好的验证**：编写样例元组的过程中发现了多处设计问题（如金额不一致、关联缺失），说明样例数据不仅是演示，更是验证设计的重要手段
- **团队协作效率高**：三人分工负责不同的表，统一规范后并行推进，交叉评审时互相发现问题，比独立完成质量更高
