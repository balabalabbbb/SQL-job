# 第三周 - 阶段报告

## 一、设计思路

### 1.1 本周目标

第三周的核心目标是**使用SQL脚本从空数据库开始创建数据库和数据表，完成基础数据的新增、修改、删除和查询**，具体包括：

1. 创建数据库与数据表：根据第二周的数据字典，为六类核心对象选择合适的数据类型并创建表
2. 定义表结构：按照第二周确定的字段名、数据类型、长度、是否允许空、默认值，设置主码、候选码、外键、非空、默认值和检查约束
3. 添加样例数据：把第二周的样例元组转换为INSERT语句，并增加更多数据便于后续查询测试
4. 完成增删改查：对商品、库存、订单相关数据分别完成插入、查询、修改、删除操作
5. 验证脚本可复现：在空数据库中按说明重新执行脚本，确认能够得到相同的表结构和样例数据

### 1.2 脚本设计原则

本周SQL脚本设计遵循以下原则：

1. **模块化分离**：将建库、建表、插数、CRUD分为四个独立脚本，便于分步执行和调试
2. **执行顺序明确**：建表顺序严格按照外键依赖关系（先被引用，后引用），删除顺序相反
3. **约束完整**：每张表都包含主码约束、唯一约束（候选码）、外键约束、非空约束、默认值、检查约束
4. **数据类型合理**：金额用DECIMAL避免浮点误差，时间用DATE/DATETIME，字符串用VARCHAR，自增ID用INT
5. **注释详细**：每个字段都有COMMENT注释，每个操作前有说明，便于理解和维护
6. **可复现**：脚本可以在空数据库中从头执行，得到相同的结果；DROP TABLE IF EXISTS保证重复执行不报错
7. **安全操作**：UPDATE和DELETE前先用SELECT确认目标行，避免误操作；CRUD脚本最后清理测试数据

### 1.3 约束设计

本周实现了五类完整性约束：

| 约束类型 | 实现方式 | 示例 |
|---|---|---|
| 实体完整性 | PRIMARY KEY | product.product_id、orders.order_id |
| 参照完整性 | FOREIGN KEY | inventory.product_id → product.product_id |
| 域完整性 | NOT NULL + DEFAULT + CHECK | product.sale_price NOT NULL DEFAULT 0, CHECK (sale_price > 0) |
| 唯一完整性 | UNIQUE | member.phone、employee.login_account |
| 用户定义完整性 | CHECK约束 | order_item.subtotal = quantity * unit_price |

### 2.2 数据表创建

- **时间**：第3周第1-2天
- **负责人**：胡海博（商品、库存表）、胡懿桓（订单、订单明细表）、林一（会员、员工表）
- **工作内容**：
  - 根据第二周的关系模式设计，编写 `02_create_tables.sql`
  - 确定建表顺序：product → member → employee → inventory → orders → order_item
  - 为每张表定义所有字段，包括字段名、类型、长度、是否允许空、默认值、注释
  - 为每张表设置主码约束（PRIMARY KEY）
  - 为候选码设置唯一约束（UNIQUE）：inventory.product_id、member.phone、employee.login_account、order_item(order_id, product_id)

  - 每张表使用InnoDB存储引擎，支持事务和外键
  - 交叉评审：检查外键字段与引用字段的类型、长度是否完全一致

### 2.3 样例数据插入

### 2.4 CRUD操作实现

- **时间**：第3周第4-5天

- **工作内容**：
  - 编写 `04_crud_operations.sql`，包含商品、库存、订单三张表的完整CRUD操作
  - **商品表**：
    - Create：插入新商品P0011旺仔牛奶
    - Read：3种查询（在售商品列表、饮料毛利分析、缺货下架商品）
    - Update：修改商品价格和供应商
    - Delete：删除商品（先检查外键引用）
  - **库存表**：

    - Delete：删除订单（先删明细，再删主表）
  - 每个UPDATE和DELETE前都先用SELECT确认目标行
  - 每个操作后都有验证查询，展示执行结果
  - 增加约束验证部分：演示外键、唯一、检查、非空约束如何拒绝非法数据

### 3.3 遇到的问题与解决

| 问题 | 解决方式 |
|---|---|
| 建表顺序错误导致外键创建失败 | 严格按照外键依赖关系排序：先创建被引用表（product、member、employee），再创建引用表（inventory、orders、order_item） |
| 订单总金额与明细合计不一致 | 交叉验证每个订单的total_amount等于其所有明细subtotal之和，修正了2处不一致 |
| 员工密码明文存储不安全 | 改为bcrypt哈希值示例，字段长度设为64，注释中明确说明严禁明文存储 |
| CHECK约束在旧版MySQL不生效 | 在复现说明中明确要求MySQL 8.0.16+，并提供使用触发器的替代方案 |
| 删除订单时外键约束报错 | 先删除订单明细（order_item），再删除订单主表（orders），在脚本中明确说明删除顺序 |
| 重复执行脚本时报表已存在 | 所有建表语句前加DROP TABLE IF EXISTS，按删除顺序排列，保证脚本可重复执行 |
| 中文乱码问题 | 数据库和表都设置DEFAULT CHARSET=utf8mb4，在复现说明中提醒客户端设置SET NAMES utf8mb4 |

### 3.5 心得体会

通过第三周的SQL脚本编写和CRUD操作实现，小组成员深刻体会到：

- **设计是实现的基础**：第二周清晰的关系模式设计大大加快了本周的SQL编写速度，每个字段的类型、长度、约束都有明确依据
- **约束是数据质量的保障**：通过主码、外键、唯一、检查、非空五类约束，能够在数据库层面保证数据的完整性和一致性，比应用层校验更可靠
- **执行顺序很重要**：建表、插数、删除都有严格的顺序要求，违反外键依赖会导致操作失败，这体现了关系数据库的严谨性
- **UPDATE和DELETE要谨慎**：先SELECT确认目标行再执行修改/删除，是避免误操作的好习惯，尤其是WHERE条件写错可能影响大量数据
- **样例数据要体现关联**：孤立的数据没有意义，样例数据必须体现表与表之间的关联关系，才能用于测试连接查询和外键约束
- **注释和文档不可少**：详细的字段注释和复现说明让其他人能够快速理解和使用脚本，也便于自己后续维护
- **团队协作效率高**：三人分工负责不同的表和CRUD操作，统一规范后并行推进，交叉评审时互相发现问题，比独立完成质量更高
