# 第四周阶段报告

## 一、设计思路

### 1.1 本周目标
第四周是第一阶段（第1-4周）的收官周，目标是完成数据库原型v0.1的全部功能：多表查询、统计视图、完整性约束验证和角色权限管理，并确保从空数据库开始可以完整复现整个系统。

### 1.2 经营场景与业务流程
本项目以校园小卖部为经营场景，核心业务流程包括：
- **商品管理**：商品信息维护、分类管理、价格管理
- **库存管理**：库存数量跟踪、预警阈值设置、货架位置管理
- **订单管理**：订单创建、订单明细、支付方式、订单状态
- **会员管理**：会员注册、等级管理、积分管理、消费记录
- **员工管理**：员工信息、岗位、登录账号、销售业绩

### 1.3 数据边界
**进入数据库的信息**：
- 商品基础信息（名称、分类、价格、单位、保质期）
- 库存信息（数量、预警阈值、货架位置、最后更新时间）
- 订单信息（订单号、时间、金额、支付方式、状态、会员、收银员）
- 订单明细（商品、数量、单价、小计）
- 会员信息（姓名、手机号、等级、积分、累计消费）
- 员工信息（姓名、岗位、登录账号、入职时间）

**暂不进入数据库的信息**：
- 供应商信息（采购流程暂未纳入）
- 财务报表（收入、成本、利润核算暂未纳入）
- 促销活动（优惠券、折扣活动暂未纳入）
- 员工考勤（排班、考勤暂未纳入）
- 顾客详细信息（非会员顾客仅记录订单，不记录个人信息）

## 二、实验过程

### 2.1 多表查询设计（query.sql）

围绕业务问题设计了16个查询，覆盖：

**多表连接查询（4个）**：
- 订单完整详情：orders + order_item + product + member + employee 五表连接
- 所有订单及会员信息：orders LEFT JOIN member（含非会员订单）
- 商品库存状态：product + inventory，含预警状态计算
- 员工销售业绩：employee LEFT JOIN orders，含订单数和销售额

**聚合统计查询（5个）**：
- 按商品分类统计销售情况
- 商品销量排行榜TOP 5
- 会员消费统计（HAVING筛选消费>100元）
- 按支付方式统计订单
- 按日期统计每日销售

**子查询（5个）**：
- 销量高于平均水平的商品（FROM子查询）
- 从未被购买过的商品（NOT IN子查询）
- 每个分类中售价最高的商品（关联子查询）
- 会员最近一次消费信息（IN + 最大时间子查询）
- 库存价值分类占比（子查询计算总值作为分母）

**综合业务分析（2个）**：
- 商品毛利分析（毛利率、已实现毛利）
- 会员等级价值分析（人均消费、客单价）

### 2.2 统计视图设计（view.sql）

创建了7个统计视图，封装常用复杂查询：

| 视图名称 | 用途 | 包含表 |
|---|---|---|
| v_order_detail | 订单详情视图 | orders, order_item, product, member, employee |
| v_product_sales | 商品销售统计视图 | product, order_item |
| v_inventory_status | 库存状态视图 | product, inventory, employee |
| v_member_sales | 会员消费统计视图 | member, orders |
| v_employee_performance | 员工销售业绩视图 | employee, orders |
| v_daily_sales | 每日销售汇总视图 | orders |
| v_category_sales | 分类销售统计视图 | product, order_item |

每个视图都附带验证查询，确保视图返回正确结果。

### 2.3 完整性约束验证（constraint.sql）

系统验证了6类完整性约束：

**主码约束**：6个表各1个主码，验证主码唯一和非空
**外码约束**：6个外键，验证外码引用存在和删除被引用记录失败
**唯一约束**：4个唯一约束（手机号、登录账号、商品-库存、订单-商品）
**检查约束**：24个CHECK约束，覆盖价格、分类、状态、手机号格式、金额计算等
**默认值约束**：商品状态默认'在售'、订单时间默认CURRENT_TIMESTAMP
**非空约束**：商品名称、会员姓名、支付方式等关键字段NOT NULL

正例实际执行展示成功，反例以注释形式展示预期报错信息，可手动取消注释验证。

### 2.4 角色权限设计（role.sql）

基于第一周角色清单，创建4个数据库角色，遵循最小权限原则：

| 角色 | 权限范围 | 限制 |
|---|---|---|
| store_manager（店长） | 全部6张表的SELECT/INSERT/UPDATE/DELETE + 所有视图查询 | 无 |
| cashier（店员） | 商品SELECT、库存SELECT/UPDATE、订单SELECT/INSERT、明细SELECT/INSERT、会员SELECT + 3个视图 | 不能删除、不能管理员工、不能修改会员等级 |
| member（会员） | 商品SELECT、订单SELECT、明细SELECT + 1个视图 | 只读，不能查看其他会员信息 |
| guest（顾客） | 仅商品SELECT | 不能查看订单、会员、员工、库存 |

创建4个测试用户并分配角色，实际测试了8个用例（4个越权失败 + 4个正常成功）。

### 3.1 完成情况

| v0.1复现 | ✅ 完成 | 从空库依次执行全部脚本可复现 |

### 3.2 关键发现

1. **INNER JOIN vs LEFT JOIN的选择**：订单与会员的连接必须使用LEFT JOIN，因为非会员订单的member_id为NULL，使用INNER JOIN会丢失这些订单。

2. **约束验证的脚本设计**：反例测试会导致MySQL报错并中断脚本执行，因此采用注释方式呈现反例，正例实际执行，既保证脚本可完整运行，又保留了反例验证能力。

3. **角色权限的实际效果**：通过测试用户实际登录验证，确认越权操作均被MySQL拒绝（ERROR 1142），正常操作均成功，权限设计有效。

4. **视图的可更新性**：由于所有视图都包含聚合函数或多表连接，MySQL标记为不可更新（IS_UPDATABLE=NO），这符合视图用于查询统计的设计目的。

### 3.3 遇到的问题与解决

| 问题 | 原因 | 解决方案 |
|---|---|---|
| view.sql最后查询报错 | information_schema.VIEWS无CREATE_TIME列 | 改用IS_UPDATABLE和DEFINER列 |
| constraint.sql执行中断 | 反例INSERT导致MySQL报错停止 | 反例改为注释形式，正例实际执行 |
| 外码正例测试失败 | inventory表唯一约束uk_inventory_product，P0001已有记录 | 使用全新product_id先插入product再插入inventory |
| role.sql语法错误 | SET DEFAULT ROLE用了FOR而非TO | 改为MySQL 8.0正确语法TO |

### 3.4 后续优化方向

1. **存储过程**：将订单创建（主表+明细+库存扣减）封装为存储过程，保证原子性
2. **触发器**：添加库存自动预警触发器、订单金额自动计算触发器
3. **行级权限**：会员只能查看自己的订单，可通过视图或应用层实现
4. **索引优化**：根据实际查询频率进一步优化索引策略
5. **数据备份**：添加定期备份和恢复机制
